## Failures retained and tooling corrections

The original full-run report remains failed. Protected transfer staging caused a
later controlled sandbox PowerShell command to start in `C:\`; absolute reads
worked but relative operations and explicit directory changes did not. The same
engine and sandbox policy passed in a normal inherited user-profile directory.
This contrast establishes a qualification-workspace correction, not an
engine-wide fault or retrospective attribution of missing original diagnostics.
Protected staging ACLs were not relaxed.

After that correction, GLM produced invalid JSON within its request budget.
DeepSeek was rejected by actual launcher admission although its name appeared in
broader catalog output. User-authorized Kimi selection then passed. These failures
remain visible and are not folded into the accepted results.

A private preserve-uninstall helper initially rejected the installer's UTF-8 BOM
PATH marker before mutation. Its corrected owner comparison was verified against
the retained bytes and a wrong-owner negative control. No product change was
needed; rc18 source and assets remain frozen.

The reusable tooling correction on the integration branch:

- uses a normal inherited owned execution directory and exposes the running
  Python interpreter only to the test process tree;
- checks actual launcher admission with `-- --version`, then native sandbox
  cwd, relative I/O and outside-write denial before a saved-home acceptance pair;
- reads ownership markers with UTF-8 BOM support while rejecting mismatched or
  redirected ownership;
- retains installation/login by default, reports the resulting state explicitly,
  and requires `--purge` for the separate destructive lifecycle scope.

These are later qualification-tooling changes, not the runner used for the
historical original report. The accepted follow-up phases used the frozen test
modules with separately retained setup/orchestration corrections.

There is no evidence-backed reason to purge the working login or repeat accepted
live phases. Do not claim a full real-vault purge pass. If that separate scope is
required later, use an explicitly authorized disposable credential namespace and
test only its purge/recovery path; do not repeat coding or Guardian checks.
