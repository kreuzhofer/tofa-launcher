## Desktop attempt: transient DeepSeek availability failure

The maintainer reported that GLM 5.3 worked in the published rc17 desktop, then
a new DeepSeek V4.1 Flash chat in the same open client immediately failed with
HTTP 404/model-not-found. Exact GLM title, relaunch persistence and manual-title
preservation are not yet recorded for rc17. The launcher logged upstream 404;
this is not counted as a passing DeepSeek UI attempt.

A minimal request sent directly to Token Factory with the same saved login and
project reproduced the exact DeepSeek error, bypassing both launcher and desktop.
At 12:53 UTC the authenticated catalog omitted DeepSeek V4.1 Flash; its request
returned 404 in 0.317s, while GLM remained listed and returned 200 in 0.761s. At
12:54 UTC a second probe found DeepSeek in both authenticated and public catalogs
and returned 200 in 0.817s, without an intervening launcher/model/credential change.
This supports transient provider availability/catalog behavior; neither the
provider's internal cause nor permanent retirement/renaming is established.

The desktop uses a launch-time catalog snapshot under ADR 0003. A previously
available entry can therefore remain in an open picker after upstream availability
changes. No model substitution, fallback, product fix or automatic retry was added.
Three minimal diagnostic inference requests used synthetic prompts and a 32-token
output cap; follow-up catalog sampling used no inference. The maintainer then confirmed the same-client UI retry works without relaunching
or changing models. Five subsequent read-only catalog samples all included
DeepSeek and GLM. Exact title and persistence confirmation remain pending. This does not overwrite the earlier successful
Mac CLI lifecycle or turn the failed UI attempt into a first-pass success.
